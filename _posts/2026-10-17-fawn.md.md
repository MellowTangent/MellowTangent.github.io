- **Box Info:** 
	- Tier: 0
	- Name: Fawn
	- OS: Linux
	- Difficulty: Very Easy
- **Enumeration:** I started the enumeration process with a quick Nmap scan of the target system. 
  ![](/assets/img/fawn/nmap-scan.png)
  
  As we can see from the scan we found an FTP (File Transfer Protocol) service running. It is using port 21 (default for FTP) over TCP. 
  
- **Access:** The next step is obtaining access to the system using FTP so we try what has worked for us before. We point ftp toward the target machine's IP. 
  
  ![](/assets/img/fawn/ftp-failure.png)
  
  I did attempt several username and password combinations but I quickly realized that this was not going to work. I began to look at what useful command switches I could use with the FTP command. After looking over the many command options one really stood out to me. 
  
  ![](/assets/img/fawn/useful-command.png)
  
  I decided to use this command switch and see what would happen.
  
  ![](/assets/img/fawn/ftp-access.png)
  
  It looks like the FTP service was misconfigured to allow anonymous logins and that is what got me access. From here it was just a matter of familiarizing myself with the commands allowed by FTP. After looking around I found the needed commands to obtain the flag. 
  ![](/assets/img/fawn/flag-obtained.png)
  
- **Analysis:** These boxes are starting to show a real pattern where the main issue is a simple misconfiguration of a service. In this box the issue wasn't weak/missing credentials it was allowing the service to use anonymous logins. The FTP service also shares some of the common weaknesses found in telnet such as sending all communications unencrypted. FTP being an outdated protocol also means a lot of security features are tacked on or non existent. 
  
- **Remediation:** The fix here would be to not allow use of anonymous logins. However, as I stated before FTP sends all communications unencrypted which poses a real risk. Instead we would want to use the encrypted version of FTP known as SFTP (SSH File Transfer Protocol). 
  
- **Takeaways:** For this lab the main takeaway is to pick the access point with the lowest amount of friction. I could have tried numerous amounts of usernames and passwords or even better written a script to automate the brute forcing. However, here recognizing early that brute forcing would burn time for no payoff, and pivoting to enumerate the service’s actual options instead was the main lesson. From the defenders side the main lesson is knowing how to configure the services that you are using and making sure you explore all the options for doing so. In this case allowing the use of anonymous connections is what allowed me to gain access. From here a real attacker can upload malicious scripts, download files containing sensitive information such as credit card numbers, login credentials, and so on.
